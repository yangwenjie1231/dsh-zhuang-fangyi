# 双壳适配说明

本插件要改外壳布局（壁纸纱层、观测台浮层、气泡重绘），所以必须**稳定地
找到外壳元素**。本机实测发现：**桌面端与网页端跑的是两套不同的壳**，类名哈希
完全不同。这份文档记录核实结果与应对策略，避免以后重新踩坑。

---

## 一、两套壳的实测差异

| 维度 | 桌面端（本机实际运行） | 网页端 |
|---|---|---|
| 版本 | `0.2.0-rc.2` | `0.1.0-rc.7` |
| 来源 | `app.asar` 内自带 | profile 的 `node_modules` |
| AppFrame 类名 | `BynINW_frame` / `_sidebarCol` / `_centerCol` / **`_rightbarCol`** | `pI_x6G_frame` / `_sidebarCol` / `_centerCol` / **`_detailsCol`** |
| 右栏折叠属性 | `data-rightbar-collapsed` | `data-details-collapsed` |
| `shell.overlay` | 有（`[data-shell-overlay]`） | 有 |
| `shell.leading` | 有渲染方（`[data-shell-leading]`，仅 macOS） | 只声明、**无渲染方** |
| `sidebar.brand.mark` / `conversation.hero.brand.mark` | **有渲染方**（带 `FishLogo` fallback） | 只声明、无渲染方 |
| 桌面专属包 | `dsh-client-ui-sidebar-browser` / `-right` / `-files` / `-terminal` / `-documentpreview` | 无 |
| `data-*` 语义锚点 | **456 个** | 139 个 |

### 怎么确认的

```powershell
# 1. 桌面端的壳在 app.asar 里
python -c "..."   # 解析 asar header，列出 /dsh/node_modules/@deepseek-ai/*

# 2. 关键判据：类名哈希
#    app.asar 内:     BynINW ✓   pI_x6G ✗   rightbarCol ✓   detailsCol ✗
#    node_modules 内: BynINW ✗   pI_x6G ✓   rightbarCol ✗   detailsCol ✓
```

**哈希由 CSS 内容决定**，所以同一份源码编译出的哈希是稳定的 —— `pI_x6G` 在
profile 的 `node_modules` 与 `app.asar` 之外的位置一致，但两套壳的 CSS 不同，
哈希就不同。这也意味着**不能把哈希写进代码**。

### 这个发现修正了什么

- 我原先记录的 `_rightbarCol` 在**桌面端有效**、在**网页端失效**；
- 参考实现 Mornye 用的 `detailsCol` 在**网页端有效**、在**桌面端失效**。

双方各错一半。所以右栏选择器必须两个都写。

## 二、三层定位策略

按可靠性从高到低，三层同时用，互为兜底。

### 第 1 层：语义 `data-*` 锚点（最稳）

桌面壳暴露 **456 个** `data-*`，都是外壳给 React 组件打的语义标记，跨版本稳定：

| 锚点 | 用途 |
|---|---|
| `[data-rightbar-col]` | 右栏列 |
| `[data-shell-overlay]` | 浮动层（观测台浮层挂这里） |
| `[data-chat-flow-kind]` | 聊天行类型（`user` / `assistant-step` / `tool-call` / `turn-tail` / `turn-error`） |
| `[data-composer-card]` / `[data-composer-seat]` | 输入框卡片与座位 |
| `[data-composer-stats]` | 统计行（轮次/步数/缓存命中） |
| `[data-sidebar-collapsed]` | 侧栏折叠 |
| `[data-streaming="true"]` / `[data-state="running"]` | 运行中标记 |
| `[data-window-drag]` | 窗口拖拽区 |

**优先用这些**，不碰类名。

### 第 2 层：`data-plugin-css` 反查哈希（次稳）

外壳为每个 CSS Module 插入一个样式标签：

```html
<style data-plugin-css="@deepseek-ai/dsh-client-ui-layout/AppFrame.module.css"
       data-plugin="@deepseek-ai/dsh-client-ui-layout">
  .BynINW_frame{...} .BynINW_sidebarCol{...} ...
</style>
```

标签的 `textContent` 里就是该模块**当前生效**的真实类名。从中正则提取即可，
不用猜哈希。这一招学自 [Mornye-Observation-Skin](https://github.com/is-limo/Mornye-Observation-Skin)。

```js
const tag = document.querySelector('style[data-plugin-css$="/AppFrame.module.css"]')
const text = tag.textContent.replace(/\\([0-9a-f]{1,6})\s?|\\(.)/gi, (_, hex, ch) =>
  hex ? String.fromCodePoint(Math.min(parseInt(hex, 16), 0x10ffff)) : ch)  // 反转义
const cls = text.match(/\.([\w-]+_sidebarCol)(?=[\s{.:\[>,#])/)?.[1]   // -> "BynINW_sidebarCol"
```

**两个必须处理的坑**：

1. **转义类名** —— 以数字开头的类名在 CSS 里写作 `\37 yHdaG_row`，必须先反转义
   （`QueueDock.module.css` 就有）。不处理会匹配失败。
2. **标签可能还不存在** —— 插件可能先于外壳渲染。此时返回 `null`，下次再试，
   **不要抛错**。

### 第 3 层：`[class*="_后缀"]` 兜底

语义后缀（`_sidebarCol`）比哈希前缀稳定，两套壳都命中。样式表里用这一条，
保证**首帧**（JS 还没跑）就有正确样式。右栏两个后缀都要写：

```css
[class*="_rightbarCol"],   /* 桌面端 */
[class*="_detailsCol"]     /* 网页端 */
```

## 三、打标：把定位结果固化下来

定位到元素后，客户端给它们打上**本插件自己的** `data-zf-*`：

| 属性 | 打在 |
|---|---|
| `data-zf-frame` | AppFrame 外框 |
| `data-zf-sidebar` / `data-zf-center` / `data-zf-rightbar` | 三列 |
| `data-zf-rail="on"\|"off"` | body（观测台浮层显隐） |
| `data-zf-avatar` | body（头像气泡开关） |
| `data-zf-session-state` | body（会话状态，驱动状态点颜色） |

CSS 优先认这些属性。好处：**外壳换版本、换哈希时，只要定位逻辑能自愈，
样式表一个字都不用改。**

### 生命周期要点

- **幂等**：已有该属性就跳过（`mark()` 返回 `false`）。
- **可还原**：`tagged: Map<node, Set<attr>>` 记录「谁被打了什么」，卸载时逐条
  移除。不做记录就只能 `querySelectorAll` 盲删，会误伤别人打的属性。
- **清理断开节点**：React 卸载子树后，打标会跟着元素一起消失，但 `Map` 里的
  引用还在 —— 会泄漏。所以每次 `refresh()` 先 `prune()` 掉 `!isConnected` 的。

### 观察器要收窄

```js
observer.observe(document.documentElement, {
  subtree: true, childList: true, attributes: true,
  attributeFilter: [
    'data-rightbar-collapsed', 'data-details-collapsed',
    'data-sidebar-collapsed', 'data-ds-dark-theme',
    'data-chat-flow-kind', 'data-streaming', 'data-state', 'hidden'
  ]
})
```

**必须给 `attributeFilter`**：聊天区在流式输出时每帧都在变 DOM，不收窄的话
观察器每帧触发一次，白白烧 CPU。

## 四、顶栏已移除（历史教训：定位基准要选确定的）

曾经的顶栏设计（现**已整体删除**，原因见下）只留下两条仍然有效的结论。

**背景**：Windows 桌面壳给 frame 加了标题栏带：

```css
[data-windows-titlebar] .BynINW_frame{
  padding-top: var(--dsh-windows-titlebar-height);   /* 40px */
}
[data-windows-titlebar] .BynINW_frame::before{
  content:""; height: var(--dsh-windows-titlebar-height);
  background: var(--dsw-specific-sidebar-fill);
  -webkit-app-region: drag;                          /* 窗口拖拽区 */
}
```

**为什么删掉顶栏**：用户实测反馈两条 —— ① 它 `position:fixed` 浮在中栏上方，
**压住了会话标题那一行**（截图可见标题被切掉半边）；② 它显示的信息全是冗余
（头像在侧栏品牌位与助手消息旁都有，预设与会话状态在观测台里都有）。
右栏观测台因此改为**顶格**显示（`top:0`，仅 Windows 下让开 40px 标题栏）。

### 留下的有效结论

1. **不要给顶栏类控件放按钮** —— Windows 标题栏那条 40px 带子被系统占满
   （左 0–40px 窗口图标、48px 起「应用/编辑」菜单 Shadow DOM `z-index:1100`、
   右侧 ~138px 窗口按钮）。任何浮在那里的东西都会与原生 chrome 抢位置。
2. **定位基准选「确定的坐标系」**：`shell.overlay` 是 AppFrame（`display:grid`）
   的子元素，三个列与它都**没写 `grid-area`**（依赖自动放置），且 frame 在
   Windows 下有 `padding-top`。观测台浮层因此用 `position:fixed` 相对**视口**
   定位，Windows 下自己加 `--dsh-windows-titlebar-height` —— 用一点手工补偿
   换来不随壳布局变化的确定基准。
   > 教训：位置问题要用 `getBoundingClientRect` 实测（`/diag` 的 `geom` 字段），
   > 不要靠截图量像素反推 —— 我曾据此推断「overlay 被挤到第二行」，实测
   > overlay 就在 `{0,0}`，推断是错的。

## 五、观测台进官方右栏的两种方式（为什么不用 `openRightbar` 抢轨道）

桌面壳的 `ctx.layout` 服务提供：

```
selectPanel(panelId) / toggleSidebar() / openRightbar(track, fullscreen) / closeRightbar()
```

`openRightbar` 打开的是**原生右栏**（`rightbar` 插槽），由文件预览、终端、
文档预览等插件共用。**整块抢走这个 `single` 插槽**会与它们直接冲突。

本插件的分层策略（两阶段实现后的现状）：

1. **首选：注册自己的标签页**（`sidebarRightTabs` 两阶段注册 + `openTab`）
   —— 走官方 `sidebar.right.pane.tab` 扩展席位（`priority:'extension'` 不抢
   builtin），观测台成为原生右栏里**并列的一个 tab**：不占额外轨道、随原生
   一起开合、可拖拽调宽。打开时机严格「仅在面板已展开时」，不代用户展开。
2. **兜底：`shell.overlay` 浮层** —— 右栏收起时贴右侧显示；官方服务缺失
   （Web 端无 `dsh-client-ui-sidebar-right`）时自动接管。
3. 两路径由 `railOwner()` **单点裁决**，判定依据是 `tabMounted`（真的挂着
   内容）而非注册状态 —— 注册 ≠ 打开，这是实测踩过的坑。
4. 视口 < 1180px 时浮层隐藏（同 Mornye 断点），避免挤压中栏。

## 六、`shell.leading` 是死插槽（网页端）

`shell.leading` 的用途是「macOS 上侧栏收起时，在左上角放重新展开控件」。桌面壳
渲染它，但**仅在 `html[data-platform='darwin']` 且侧栏收起时**：

```js
const leadingMounted = darwin && sidebarCollapsed
```

网页端更是**只声明、无渲染方** —— 注册进去等于石沉大海。所以本插件不用它。

同理，网页端的 `sidebar.brand.mark` / `conversation.hero.brand.mark` 也只声明不
渲染。注册了在网页端不会有副作用（不会报错），在桌面端才显示 —— 这正是我们
要的，所以不需要按平台分支。

## 七、宿主模块缓存（改代码不生效的原因）

**这是最容易误判为「代码写错了」的坑。**

桌面端是**两个进程**：Electron 主进程 `spawn` 一个独立的 Node 宿主进程。插件
的 Host 半边跑在那个 Node 进程里。

Node 的 ESM 模块按**解析后的路径**缓存。`plugin_manager` 的
`set_plugin(enabled=false)` → `enabled=true` 只会：

- 卸载插件（跑 `ctx.effect` 的清理函数）；
- 重新 `apply()` —— 用的是**已经 import 过的模块对象**。

它**不会**重新 `import('./index.js')` 或 `./src/palette.js`。所以：

| 改了什么 | disable/enable 够不够 |
|---|---|
| `client.js` | ✅ 够（浏览器半边走 mtime/size 派生的 revision，HMR 会重载） |
| `index.js` / `src/*.js` | ❌ **必须重启 DSH** |

### 怎么确认跑的是哪一版

`tools/deploy.ps1` 会在部署时把 `index.js` 里的 `'__ZF_BUILD__'` 占位符替换成
时间戳。探活即可判断：

```powershell
Invoke-WebRequest http://127.0.0.1:19387/api/zhuang-fangyi/themes | % Content
# {"build":"20261005-123748", ...}
```

- `build` 是刚部署的时间戳 → 跑的是新代码；
- `build` 是旧时间戳或**字段缺失** → 宿主还在跑旧模块，需要重启 DSH。

这个标记就是为了把「代码写错了」和「进程没重载」区分开 —— 实测时我一度以为
配色改动没生效，实际是宿主缓存。

## 八、桌面端 `tapIndex` 不执行（壁纸/观测台/气泡重绘全部失效的根因）

**这是最隐蔽、代价最大的一个坑，值得单独一节。**

宿主用 `tapIndex` 往 `index.html` 的 `</head>` 前注入首帧样式：

```js
ctx.inject(['webServer'], scoped => {
  scoped.effect(() => server.tapIndex(tap), 'zhuang-fangyi: first-paint tokens')
})
```

它在 **Web 端有效**，但在**桌面端从来不会执行**。原因在 `app.asar` 的
`dsh-app://` 协议处理器：

```js
protocol.handle(SCHEME, (request) => {
  const url = new URL(request.url)
  if (url.hostname === "app") {
    if (url.pathname === "/" || url.pathname === "/index.html" || ...)
      return serveWebDocument(request,
        join(resources.dsh, "node_modules", "@deepseek-ai", "dsh-web-frontend", "dist"))
    ...
  }
})

function serveWebDocument(request, root) {
  body = await readFile(target)                    // ← 直接从磁盘读
  const content = body.toString().replace("<head>",
    "<head><script>globalThis.__DSH_BOOT_READY__ = Promise.withResolvers()</script>")
  // ↑ 只注入这一个脚本，完全不经过 Host 的 HTTP 服务
  return new Response(content, ...)
}
```

也就是说，桌面渲染进程**直接从磁盘读 `index.html`**，绕过了 Host 的
webServer —— 所以 `tapIndex` 注册的回调根本没机会跑。

### 症状

`structureStyle()` / `structureCss()` 的全部 CSS（壁纸、纱层、观测台、气泡重绘）
**一个字都不会出现**。但 token 是由浏览器半边 `overrideTokens` 独立生效的，所以看起来
「**只改了配色**」—— 这正是最初那条反馈的真正原因。不是壁纸被纱遮住了，是
壁纸的 CSS 压根不存在。

### 修法

两条路都走，**同一份 CSS、两种形态**：

| 路径 | 适用 | 形态 | 机制 |
|---|---|---|---|
| `bootStyle()` → `tapIndex` | Web 端 | `structureStyle()`（**带 `<style>` 标签**） | 服务端注入 HTML，首帧即生效（无闪烁） |
| `/api/zhuang-fangyi/style.css` → 客户端 `ensureStyle()` | **两端都走** | `structureCss()`（**纯 CSS**） | 客户端 `fetch` 后自建 `<style id="zf-style">` 插进 head |

桌面端只有第二条路，所以它是**桌面端唯一的 CSS 来源**。Web 端两条都走：
`tapIndex` 保证首帧不闪，客户端那条是幂等兜底。

### ⚠️ 为什么两条路的形态必须分开（实测踩过，代价极大）

客户端插样式表用的是：

```js
el.textContent = css      // el 是客户端自建的 <style id="zf-style">
```

如果 `/style.css` 发出去的内容**自带 `<style id="zf-boot-css">` 与 `</style>`**
（即直接复用 `structureStyle()` 的产物），浏览器会把 `<style id=...>` 当成
**CSS 文本**解析 —— 非法起始 token → 进入错误恢复 → **紧随其后的 `html{}`
规则块被整块丢弃**。

症状极具迷惑性：

| 观察 | 原因 |
|---|---|
| 纱色 `--zf-veil` 正常 | 它是 JS **行内**写的字面 rgba，不依赖样式表 |
| `--zf-art-src` 计算值为空 | 行内写的是 `var(--zf-art-<id>)`，而被引用变量定义在**被丢掉的 `html{}` 块**里 → 整条属性失效 |
| `.zf-rail` 等规则正常 | 它们在文件后半段，错误恢复后能照常解析 |
| 结论 | **壁纸怎么都出不来**，而观测台样式看着完全正常 |

所以：`structureCss()` 是**唯一**的 CSS 来源，`structureStyle()` 只是给它套上
标签供 `tapIndex` 用。有专门的回归测试断言「`/style.css` 的形态必须是纯 CSS」。

### ⚠️ 更正：`tapIndex` 不是唯一的口子 —— `webserver/index-inject` 才是给插件用的

我一度据此推断「桌面端改不了首帧、插件碰不到开机卡片」，**这个结论是错的**。
参考实现 [dsh-550c-boot](https://github.com/yannicksong0106/dsh-550c-boot) 证明
官方另留了一条**给插件的公开注入通道**：

```js
ctx.on('webserver/index-inject', table => {
  table.push({ kind: 'style',  text: '...' })
  table.push({ kind: 'script', placement: 'head', text: '...' })
})
```

行类型（源码实测）：`global` / `style` / `script` / `script-src` / `html` / `meta`。
两个载体都会应用这张表，且**都在内核建开机卡片之前**：

| 载体 | 应用方式 |
|---|---|
| Web | 渲染进 `index.html` 的 `<head>`，早于 shell 的 module script |
| 桌面 | 在 settle `__DSH_BOOT_READY__` **之前逐行应用**：`script` 行走 `createElement` 所以会执行 |

**三者的区别要分清**：

| 通道 | 桌面端是否执行 | 时机 |
|---|---|---|
| `tapIndex` | ❌ 从不执行（`dsh-app://` 直读磁盘） | — |
| `webserver/index-inject` | ✅ 执行（载体逐行应用） | **内核建卡片之前** |
| 客户端插件（`shell.overlay`） | ✅ | 卡片移除之后（实测晚 271ms） |

实测时序（参考项目用 CDP 从导航开始计时）：开机卡片 67ms 出现 → 客户端遮罩
338ms 挂上 → 卡片 517ms 移除。**中间 271ms 是客户端怎么调 z-index 都盖不住的** ——
所以「盖住官方开机卡片」这件事**只能**走 `index-inject`。

本插件因此用它注入首帧（`#zf-first-frame` 纯色遮罩 + 把 `[data-dsh-boot]` 按成
`visibility:hidden`），并由客户端在立绘挂载时调 `window.__zfFirstFrame.end()`
**同一帧交接**。首帧脚本自带自保撤离（卡片消失 / 12s 超时），客户端出问题也不会挡住界面。

### 连带教训

1. **不要假设「宿主能改 HTML」就等于「两端都能」** —— 桌面端有独立的资源加载
   路径（`dsh-app://` 协议 + `app.asar`）。
   **但也别因此推断「插件改不了」** —— 先找官方有没有留通道
   （`webserver/index-inject` 就是），再看参考实现怎么做。
   我在这条上误判过一次，代价是白做了一版「等 boot 退场再接住」的方案。
2. **样式表加载失败不能阻断启动**：`ensureStyle()` 的失败只 `console.warn`，
   配色仍由 token 层生效（已有测试覆盖）。
3. **客户端不要重复实现 CSS**：走 `/style.css` 取宿主同一份产物，避免两处分叉。
4. **同源产物给不同消费者时，形态要分开**：`textContent` 要纯 CSS，
   注入 HTML 要带标签 —— 别指望一个字符串同时满足两边。

## 九、纱层之上还有一层不透明底（右栏 dockkit pane）

**症状**（用户反馈）：「开始页背景还是黑色的」「tab 条背景也还是黑色的」。

**误判方向**：先怀疑纱没写上去 / 变量没生效。实际是**纱在下面，上面还压着
一层不透明底** —— 中栏透出壁纸了，右栏整片仍黑。

**壳源码实测**（`dsh-web-frontend/dist/assets/index-*.css`，dockkit 模块）：

```css
._tabHost_6nhg2_162:not(._float_6nhg2_156),
._emptyTabHost_6nhg2_143{ background: var(--dsw-alias-bg-base) }
```

而 JS 里 **tabHost 就是 pane 本身**：

```js
className: ue(ve.tabHost, x ? ve.float : ve.pane)
children : [ tabHostHeader(含 tab 条), tabHostBody(含页面内容) ]
```

被反馈的两个元素**自己都没有 `background`**（壳 CSS 实测）：
`.unKlVG_guide`（开始页容器）与 `._tabStrip_6nhg2_237`（tab 条）的规则里
都没有背景声明 —— 黑色 100% 来自 pane 的 `bg-base`，它盖住了我们画在
`rightbarCol` 上的纱。

**修法**：壁纸开启时让 docked pane 透明，露出下面**已有**的那层纱 ——
用与中栏同一个 `--zf-veil`，所以可见度天然一致、滑杆一起跟随：

```css
body[data-zf-wallpaper] [data-dockkit-pane],      /* 语义锚点：docked pane */
body[data-zf-wallpaper] [data-dockkit-empty],     /* 空 pane */
body[data-zf-wallpaper] [class*="_tabHost"]:not([class*="_float"]),  /* 后缀兜底 */
body[data-zf-wallpaper] [class*="_emptyTabHost"]{ background:transparent !important }
```

这里**只写 `transparent`，不再涂一遍纱** —— 纱已经在 `rightbarCol` 上，
涂两次会比中栏深一档。

**三处刻意的「不碰」**：

- 浮窗 pane（`data-dockkit-float`）保持官方 `bg-layer-2` 不透明底 ——
  弹出窗口需要实体感（官方规则里那个 `:not(._float_)` 就是这个意思）；
- 官方拖拽停靠时的 `_dockScrim_`（`bg-base` 72% + blur）不动；
- active tab 的选中色 chip（`--dsw-alias-markdown-tag`）保留 —— 它是状态指示，
  透明掉就看不出当前在哪一页；
- 开始页的入口卡片（`.unKlVG_entry`，官方 `bg-layer-1`）保留不透明 ——
  它是按钮，压不住字就不好用了。

**锚点为什么用语义属性**：`data-dockkit-pane` 只在 pane **有标签页**时才渲染
（源码里是 `!x && w ? a.id : undefined`），所以必须再补一层类名后缀兜底；
空 pane 的属性是 `data-dockkit-empty`（打在 `_emptyTabHost_` 上）。

### 同一类的第二个面：左栏（会话列表）

用户接着贴了左栏整棵 DOM 说「这个地方也变成透明的」。壳源码实测：

```css
.BynINW_sidebarCol{ background:var(--dsw-specific-sidebar-fill); … }
._2H3hWW_root    { background:var(--dsw-specific-sidebar-fill); … }  ← 内层又铺一层
[data-platform=darwin] ._2H3hWW_root{ background:0 0 }               ← 只有 macOS 透明
```

列与内层是**两层同色不透明底**；macOS 那条 `0 0` 恰好证明结构是「列铺面、
内层透明」，官方只是没给 Windows 写后一半。

修法与右栏不同，**更省事也更稳**：不去点名内层组件，而是**在列上把
`--dsw-specific-sidebar-fill` 置为透明**（自定义属性按最近祖先解析）：

```css
body[data-zf-wallpaper] [class*="_sidebarCol"]{
  --dsw-specific-sidebar-fill:transparent !important;   /* 内层组件的底跟着透明 */
  background:var(--zf-veil-sidebar) !important;         /* 列上仍是那层纱 */
}
```

| 做法 | 依赖类名哈希 | 首帧 | 内层再多包一层 |
|---|---|---|---|
| 点名内层组件 | 要 —— 而它的本地名是 `root`，写 `[class*="_root"]` 会误伤一大片 | 要等客户端打标 | 漏 |
| **在列上改 token** | **不要** | **纯 CSS，首帧生效** | **一起透明** |

⚠️ 加 `!important`：外壳 presenter 会把 token 写成**行内样式**，而 token 的作用域
在这里是「列及其子树」，不是全局 —— Windows 原生标题栏那条探针读的是同一个
token，它是 `body` 的子元素，**两者互不影响**。

顺带一处：会话列表底部的渐隐官方是「透明 → `--dsw-specific-sidebar-fill`」，
token 置透明后这条会整条失效（透明渐到透明），列表底部变成硬切 —— 所以单独把
它改成渐到同一层纱色。

### 同一类的第三个面：输入区那条「座位」渐变

用户贴了输入区整棵 DOM 说「这里的黑色渐变背景也给去掉」。壳源码实测
（`@deepseek-ai/dsh-client-ui-conversation/lib/client.js` 里内联的 CSS）：

```css
.Dc7zOa_composerSeat{ z-index:7; position:sticky; bottom:0;
  background: linear-gradient(180deg,
    color-mix(in srgb, var(--dsw-alias-bg-base) 0%, transparent) 0px,
    var(--dsw-alias-bg-base) 36px) }
/* 实际生效的是带状态祖先的两条： */
.Dc7zOa_root[data-phase=active] .Dc7zOa_composerSeat,
.Dc7zOa_embeddedBody[data-content-phase=active] .Dc7zOa_composerSeat{ … 同上 … }
```

官方用意是好的：输入条坐在一个 sticky/absolute 的「座位」上，消息从它底下滚过去，
渐到不透明底色能让文字消失在输入区上方。**但壁纸模式下 `bg-base` 是主题的不透明
底色** —— 于是那里成了一条黑色渐变带。

处理同上：壁纸开启时把它置透明（`[class*="_composerSeat"]`，本地名是该模块专有的，
比哈希稳；两条官方规则都带 `!important`，我们靠选择器权重 + `!important` 压过）。
代价如实记下：座位不再遮滚动中的文字，消息会显示到输入卡上沿 —— 卡片本身不透明，
所以只在它上方那圈留白里看得到。

> 这类问题的**共同信号**：某个区域「和别处不一样地黑」。三个面（右栏 pane、
> 左栏内层、输入区座位）都是同一种病 —— 壳在纱之上又铺了一层不透明底，而它的
> 用意（层次、渐隐、可读性）在**不透明配色**下成立，在壁纸下不成立。

### 连带教训

**「让某块透明」= 找出所有压在它上面的不透明层，而不是给最外层加 alpha。**
多层叠加时 alpha 会连乘（第八节那个「两层各 0.83 只剩 0.69」是同一个坑的
另一种形态）；正确做法是**只保留一层纱**，把它上面每一个不透明底逐个摘掉。

判断依据不能靠猜：要从壳源码里读出**谁声明了 `background`**。这次的路径是
`rg` 直接扫 `app.asar` 里的 CSS —— 桌面壳是打包的 asar，里面的文本**未压缩**，
`rg -a -o '\.[^{}]*_6nhg2_[^{}]*\{[^}]*\}' app.asar` 就能把整个 dockkit 模块的
规则一条不落捞出来。这比在浏览器里逐层 DV 快得多，也准得多。

## 十、透明度只有一个来源：观测栏不再自己算一档

用户：「观测栏的透明度跟随全局，不要单独设置」。

先把事实摆清 —— **设置里本来就没有**观测栏的透明度（只有 `rail` 开关与
`railWidth` 宽度）。问题在实现层：观测栏走自己的一套 —— 私有变量
`--zf-rail-veil` + 私有底色 `--dsw-alias-bg-layer-1` + 私有兜底 62%。

它的**数值**确实来自同一个滑杆（`keep = 1 - 背景不透明度`），但它是在中栏那层纱
**之上又涂一层**：

| 滑杆 | 中栏那层纱 | 观测栏再叠一层 | 实际观感 |
|---|---|---|---|
| 14%（默认） | 0.86 | 0.86 | **0.98** —— 几乎全实 |
| 90% | 0.10 | 0.10 | **约 0.19** —— 仍比别处实 |

**数值同源 ≠ 观感同源。** 修法：观测栏背景**透明**，什么都不涂 —— 露出的就是
它下面中栏那层纱，所见即全局那一档，结构上不可能再不一致。分隔交给 `border-left`。

`backdrop-filter` 保留：它**不改变透明度**（纱是一层纯色，模糊它还是那个色），
只把壁纸细节糊掉，是高档位下小字号的可读性保险。私有变量与 62% 兜底一并删除
（CSS 一处、客户端两处写入 + 一处清理，全都删干净，并有断言锁住「一个字都不剩」）。

### 连带教训

**「跟随全局」的判据不是「引用了同一个变量」，而是「最终画出来的那一层是谁」。**
引用同一个 `keep` 只说明数值同源；只要它还在别人已经涂过的层上再涂一次，
观感就一定不同 —— 这又是 alpha 连乘的同一个坑（第八、九节）。

写测试时也要跟着换判据：原先「观测台与侧栏在每一档都同步」是拿**两个 alpha 相等**
来证的，现在观测栏恒为 0，等号不再成立 —— 正确的判据是「观测栏自身 alpha 恒 0，
透过去看到的那层等于全局那一档」。断言不改，测试就会变成**用旧契约给新实现判分**。

## 十一、变量「声明在哪一层」决定优先级（shiki token 色踩过）

要让某个 `--dsw-*` / `--shiki-*` 变量在我们的主题里生效，**写在哪一层**是有讲究的
—— 自定义属性按**最近祖先**解析，不看选择器权重的绝对值。

外壳实测（两层各一套，明暗分开）：

```css
:root{ --shiki-token-keyword:#d6336c; --shiki-token-string:#2f9e44; … }      /* 亮色 */
body[data-ds-dark-theme]{ --shiki-token-keyword:#faa2c1; --shiki-token-string:#69db7c; … }  /* 暗色 */
```

于是「写 `html` 行内」这种看起来最稳的做法，在暗色下**会被 `body` 那条压回去**：

| 写在哪 | 亮色 | 暗色 |
|---|---|---|
| `html` 行内 | ✓ 生效 | ✗ 被 `body[data-ds-dark-theme]` 压回外壳默认色 |
| **`body` 行内** | ✓ 生效 | ✓ 生效（行内样式优先于普通样式表规则） |

**判据**：外壳在**哪一层**声明过这组变量，我们就写在**同一层**（或更近的祖先）上。
同类还有侧栏的 `--dsw-specific-sidebar-fill`（在 `body` 上与列上各有一份，我们
在**列**上改，作用域正好只覆盖侧栏子树）。

两种写法都在真实引擎里量过：写 body → `rgb(18, 52, 86)`（我们的值）；
写 html → `rgb(250, 162, 193)`（外壳暗色粉）。用例 73 有这两条实测断言。

### 第二个实例：阅读宽度（B7）

外壳把 `--dsh-chat-content-width` 声明在 `[data-conversation-content]` **自己**身上，
而且它自己还会往那个元素写行内 `--dsh-chat-user-width`：

```css
.Dc7zOa_body{ --dsh-chat-content-width:
  var(--dsh-chat-user-width, clamp(680px, calc(列宽 * .64), 920px)) }
```

于是规则更狠一层：**元素自己的声明赢过任何继承值** —— 写 `html` / `body` 完全
无效，只能写在那个元素本身上（客户端 `el.style.setProperty(…, 'important')`）。
「标准」档 = 移除声明，把外壳自己的宽度手柄一起还回去。

顺带一条实测结论：**行内声明即使不带 `!important` 也已经赢过外壳那条样式表规则**
（行内 > 作者样式表）。我们仍然加 `!important`，是防外壳哪天把它也改成行内写。
这类「预期与实测不符」的地方，用例 74 里都按实测值断言（第一版按想象写了
「不加 important 会被压回」，跑出来才知道是错的）。
